# 파일 중심 웹툰 업로드 (2026-11-15)

운영 적용 전 검토용이다. 이번 작업은 분리된 로컬 DB·Auth·Storage에서만
적용·검증했고 운영 배포·SQL·Storage·Nginx 변경은 실행하지 않았다.

## 사용 흐름

`/admin/webtoons`에서 PDF 한 개 또는 PNG/JPEG/WebP 여러 장을 선택하거나
드롭한다. 파일명은 자연 정렬되고 이미지 순서를 변경할 수 있다.
업로드·최적화 후 공개 화면과 같은 PDF 뷰어/세로 이미지 형태로 미리보기하고,
게시물 제목 하나를 입력한다. 팝업 기본값은 꺼짐이다. 체크하면 현재 팝업을
새 게시물로 교체하며 기본 일정은 게시 시점부터 7일, 기본 문구는 제목이다.
일정·문구·연재 선택·회차 번호·표지 교체는 추가 설정에 있다.

작품·회차는 내부에서 비공개로 생성한다. 기존 공개 연재에 새 회차를 추가할
수 있지만 기존 연재의 제목·표지·공개 여부는 변경하지 않는다. 신규 작품은
첫 페이지에서 표지를 생성한다. 기존 관리 화면과 홍보 설정은 별도 접힌
영역에 보존했다. 기존 작품·회차·업로드 파일을 일괄 변경하지 않는다.

## 업로드·보관·복구

- PDF 50MiB/200페이지, 이미지 장당 10MiB/최대 100장과 기존 검증을 유지한다.
- PDF는 검증 worker에서 원래 순서를 유지하여 object stream 구조를 다시
  직렬화한다. 이미지를 재인코딩하거나 페이지를 래스터화하지 않는다.
  결과가 원본보다 크면 원본 바이트를 별도 열람용 키에 저장한다.
  큰 용량 감소를 보장하지 않는다. 원본은 같은 private 버킷의 별도
  `.original.pdf` 키에 보존되며 공개 media ID를 발급하지 않는다.
- 첫 페이지만 표지 생성용으로 렌더링하고 canvas와 PDF task를 해제한다.
  기존 PDF 뷰어는 주변 최대 5 canvas/총 750만 화소 상한을 유지한다.
  전체 PDF 바이트 다운로드는 기존과 같으며 Range 스트리밍 개편은 아니다.
- 서버 draft와 사용자별 localStorage ID로 새로고침 후 완료 파일·순서를
  복구한다. 브라우저는 로컬 파일 핸들을 저장하지 않으므로 미완료 파일은
  다시 선택해야 한다. SHA-256으로 같은 파일인지 확인한다.
- 각 파일의 고정 UUID를 `X-Upload-Id`로 전송한다. 서버에 ready 행이 있으면
  반환하므로 응답 유실 후 재시도에도 성공 파일을 중복 생성하지 않는다.
- 프로세스가 중단되어 uploading 행만 남은 경우는 자동 복구 대상이 아니다.
  해당 임시 업로드 취소/정리 후 다시 시작해야 한다. 다중 인스턴스 작업 큐나
  장기 백그라운드 최적화 서비스를 도입한 것은 아니다.
- 실패 시 성공 파일은 재시도를 위해 비공개로 보관한다. 취소는 이 draft의
  참조되지 않은 파일만 삭제한다. 공개/기존 참조 파일은 유지한다. 취소 재시도는
  가능하며 기록용 비공개 placeholder 작품·회차 행은 남긴다.
- 게시 가능 여부는 서버에서 전체 파일·종류·소유 작품·ready 상태·표지를
  다시 계산한다. 클라이언트 ready 값은 신뢰하지 않는다. 게시 RPC가 회차,
  신규 작품, 선택 팝업을 한 트랜잭션에서 반영하고 충돌하면 모두 롤백한다.

## 권한 및 배포 범위

추가 migration: `20261115090000_add_webtoon_upload_drafts.sql` 하나.

- RLS를 켠 `webtoon_upload_drafts` 테이블: 일반 역할의 모든 권한 회수,
  service_role만 사용. 서버는 매 요청 실제 관리자·정지 여부와 draft 소유자를
  검사한다. Origin이 있으면 서비스 Host/Proto와 동일한지 검사한다.
- service_role 전용 RPC `webtoon_start_upload`, `webtoon_publish_upload`,
  `webtoon_cancel_upload` 추가. public/anon/authenticated 실행 권한 없음.
- 기존 `webtoon_claim_orphans`는 편집 중 draft의 작품 파일을 정리하지 않게
  변경한다. 기존 cover/page/pdf 참조 보호는 유지한다.
- 기존 테이블의 데이터나 기존 RLS·Storage 정책은 변경하지 않는다.
  draft 소유 Auth 사용자가 삭제되면 draft만 cascade 삭제되어 기존 사용자
  삭제를 막지 않는다. 게시물·파일은 자동 삭제하지 않는다.
- 기존 private 버킷·정책과 업로드 URL을 재사용한다. Nginx의 기존 이미지
  `12m`, PDF `52m`가 유지되면 추가 Nginx 변경은 필요 없다. JSON draft는
  64KiB 이하로 제한한다. 새로운 대용량 URL은 만들지 않았다.
- 새 worker 패키지/시스템 의존성/유료 서비스/OAuth 설정은 필요 없다.

승인 후에는 백업 갱신 → migration 트랜잭션 적용 → 새 Linux 릴리스 빌드/
loopback 검증 → 전환 순서가 필요하다. migration 실패는 트랜잭션 전체를
롤백하고 전환하지 않는다. 앱 장애는 기존 앱 릴리스로 전환한다. 추가 테이블,
게시물과 원본·열람 파일은 롤백 시 자동 삭제하지 않는다. 기존 앱은 추가
테이블을 무시하며 기존 저장/조회 계약은 유지된다. worker 파일과 pdf-lib
배포 추적 규칙도 기존 것을 사용한다.

## 실제 PDF 실패 조사와 검증 결과

사용자 제공 실제 30페이지 PDF(11,344,754바이트)를 로컬에서 사용했다.
기존 UI/API 업로드도 201로 성공했고 미리보기·비공개 저장까지 통과했다.
현재 운영 접근 로그 범위에는 PDF 업로드 POST가 없었고, 확인한 오류 로그에서
worker 누락/메모리/시간 초과/권한 오류의 증거를 찾지 못했다. 따라서 운영
업로드 실패 원인은 아직 확인되지 않았다. 파일 크기, 프록시, 인증, Storage,
검증 worker 중 특정 원인으로 단정하거나 운영 문제가 해결됐다고 보고하지 않는다.
운영에서 실제 업로드 요청을 재실행하면 Storage 쓰기가 발생하므로 이번에는
실행하지 않았다. 실패 당시 브라우저 요청/응답 관찰이 추가로 필요하다.

새 흐름의 실제 PDF 업로드 → 열람용 구조 최적화 → 자동 표지 → 미리보기 →
제목 → 임시저장 → 새로고침 복구 → 팝업 → 게시 → 모바일 공개 열람 통과.
열람용 파일은 11,340,873바이트였다. 원본과 결과의 첫/마지막 페이지를
동일한 Poppler 설정으로 렌더링한 PNG의 해시가 각각 일치했다. 한글 시각 확인,
1/15/30페이지 이동, 125% 확대와 30페이지 이어보기 통과. 순차 이동 중
canvas 수/화소 상한을 확인했고 샘플 JS heap은 약 35.1→34.6MiB였다.
이는 브라우저 전체 RSS/최대 메모리나 모든 기기의 성능 보장은 아니다.

합성 이미지 3장 자연 정렬·수동 순서 변경, 중간 503 실패 후 새로고침·재선택·
재시도, 성공 파일 요청 중복 없음, 공개 전 404/게시 후 200, 모바일 표시 통과.
기존 로컬 작품·회차·파일 행을 전후 비교하여 보존을 확인했다.
추가 API 검사에서 생성/업로드 멱등성, 미완료/빈 제목 게시 차단, 익명 401,
일반 사용자 403, 외부 Origin 403, 비공개 파일 404, 취소/정리 재시도 통과.
기존 관리자 메뉴·세션·정지·로그아웃·모바일 접근 검사도 통과했다.

Node 22.23.0 타입 검사·lint·일반 빌드를 실행했다. lint는 기존 경고를
포함해 0 errors이며 최종 결과는 WORKLOG에 기록한다. preview 모드나 환경
변수 검증 우회는 사용하지 않았고 sitemap은 로컬 테스트 데이터만 읽었다.
실제 PDF·계정 파일·토큰·검사 화면과 합성 데이터는 Git/운영 배포물에 넣지 않는다.
